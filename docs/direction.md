## 1. 제품 정의

**정형 데이터의 품질 문제와 주요 통계적 특성을 자동으로 탐지하고, 분석 과정을 단계별로 안내하는 EDA 지식 베이스 + 실습 도구 통합 사이트.** AI 기반 해석·질의응답은 선택 기능으로 부가함.

한 문장 기준:
> 코드를 쓰지 않고, 질문을 설계하지 않고, 파일 하나로 데이터의 상태와 다음 할 일을 파악함.

**도구는 제품, 사이트는 리소스**임. 도구가 계산을 수행하고, 지식 베이스가 그 결과의 의미를 설명함. 두 층이 상호 링크로 연결됨(축 6).

명시적으로 배제하는 포지셔닝:
- ~~AI 기반 자동 EDA 웹 서비스~~ — AI를 핵심에 두면 API Key 의존성 때문에 무료 사용자에게 빈 서비스가 됨
- ~~정형 데이터 자동 EDA 웹 서비스~~ — ydata-profiling·DataPrep과 기능적으로 겹쳐 차별성 없음
- ~~콘텐츠 없는 순수 도구 사이트~~ — 1차 타깃의 검색 유입 경로가 없고, 사이트 신뢰도·수익화 요건 모두 미달함 (사전조사 §11 참조)

## 2. 타깃 사용자

| 우선순위 | 사용자 | 상황 | 필요한 것 |
|---|---|---|---|
| 1차 | 데이터 분석 입문자·부트캠프 학습자 | 데이터를 받았으나 어디서 시작할지 모름 | 단계별 안내 + 해석 + 다음 단계 제시 |
| 2차 | 주니어 데이터 분석가 | 신규 데이터 초기 점검 시간 단축 희망 | 품질 진단, 타깃 기반 분석, 재현 가능한 산출물 |
| 3차 | 비개발 실무자(기획·마케팅·운영) | Excel 이상의 분석이 필요하나 코드 불가 | 무설치·무코드 결과, 결과 파일 보관 |

비타깃: 실시간 스트리밍, 비정형(이미지·텍스트·로그), 대규모 DW 연동, BI 대시보드 구축.

> **3차 타깃 요구의 부분 미충족**: 사전조사 §8의 G7(재현·이력·공유 부재)에 대한 대응이 **재현만 충족하는 수준으로 축소됐음.** 백엔드를 두지 않기로 결정해(`tech-stack.md`) 결과 JSON 내보내기/불러오기로 재현은 가능하지만 **링크 공유는 Phase 3(D1 도입 전제)** 으로 밀렸음. 3차 타깃의 "공유" 수요는 MVP에서 파일 전달로만 충족됨. 이 판단은 업로드 데이터를 서버에 두지 않는 것이 더 큰 차별화라는 계산에 따른 것임.

## 3. 차별화 전략 (6축)

축 1~4는 사전조사 §10에서 도출함. 축 5~6은 조사 대상 전체가 비어 있는 영역으로 추가함.

### 축 1. 결과를 "발견(Finding)" 단위로 정리 (G1, G2)

상관행렬·통계표를 나열하는 대신, 통계적으로 유의미한 사항을 발견 목록으로 승격시킴.

```text
🔍 주요 발견
1. Age ↔ Income      강한 양의 상관관계 (r = 0.72)
2. Income ↔ Score    중간 정도의 양의 상관관계 (r = 0.64)
3. Age               결측치 없음 / 이상치 2.1% / 오른쪽으로 치우친 분포
```

각 발견은 `무엇이 발견되었는지 / 왜 문제인지 / 무엇을 하면 되는지` 3단 구성을 가짐. 특히 **ML 관점 해석**(다중공선성, 데이터 누수 후보, 클래스 불균형, 대치 시 분포 왜곡)을 포함함.

- 예: "`age` 결측 32% — 평균 대치 시 분포 왜곡 위험. 결측 여부 파생변수 생성 또는 해당 행 제외 검토 권장"
- **규칙 기반 템플릿으로 구현**(결정론적·무비용). LLM 요약은 선택 레이어(축 4)

또한 정보 과부하를 방지하기 위해 모든 그래프를 생성하지 않음.

```text
데이터 타입 분석 → 변수 특성 분석 → 통계적 특성 분석 → 중요한 관계 선택 → 대표 시각화 생성
```

### 축 2. 단계별 분석 가이드 (G4)

결과를 한꺼번에 던지지 않고 분석 흐름으로 제시함. 서비스의 성격을 "EDA Dashboard"가 아니라 **"EDA 분석 가이드"** 로 규정함.

```text
STEP 1  데이터 구조 확인
STEP 2  데이터 품질 검사        → Dataset Health Score
STEP 3  주요 발견              → Finding 목록
STEP 4  변수별 분포 분석
STEP 5  변수 간 관계 분석
STEP 6  이상치·특이점 확인
STEP 7  Target 분석            (선택)
STEP 8  EDA Summary
STEP 9  AI 해석                (선택)
```

**Dataset Health Score**: 결측·중복·상수 컬럼·고카디널리티·이상치·유효하지 않은 값을 정량화해 단일 화면으로 집약함. 임의 점수가 아니라 항목별 감점 규칙을 문서화해 산정함.

### 축 3. 타깃 기반 EDA (G3)

사용자가 타깃 컬럼을 지정하면 분석 목적이 결과 구성에 반영됨.

```text
Target 지정 → Target type 자동 판단 → Classification / Regression 분기 → 목적별 EDA 구성
```

- `target = Survived` → 이진 분류 EDA (클래스 분포, 클래스별 피처 분포, 불균형 경고)
- `target = SalePrice` → 회귀 EDA (타깃 분포·왜도, 피처별 상관 순위, 산점도)

### 축 4. AI는 계산이 아닌 해석에, 그리고 선택 사항으로 (G9)

기본 EDA는 AI 없이 완결됨. AI는 사용자가 API Key를 입력했을 때만 활성화되는 부가 레이어임.

```text
[기본 — API Key 불필요]
CSV → Pandas/NumPy/SciPy → EDA Engine → JSON → Frontend

[AI 분석 — 선택]
EDA Engine → 구조화된 EDA 결과(집계 통계만) → 사용자 API Key → LLM → 자연어 인사이트 / Q&A
```

**원본 데이터를 LLM에 전송하지 않음.** 컬럼별 통계·결측률·왜도·이상치율·상관계수 등 집계값만 전달함. 이로써 토큰 비용 감소, 처리 속도 향상, 개인정보·원본 데이터 외부 전송 최소화를 동시에 달성함. 백엔드가 없으므로 **원본은 애초에 브라우저를 벗어나지 않으며**, 이 설계는 서비스 설명 시 그 자체로 강점이 됨.

> **리스크**: 백엔드 없이 브라우저에서 LLM API를 직접 호출하려면 제공자별 CORS 정책을 통과해야 함(일부는 전용 헤더를 요구하거나 브라우저 직접 호출을 막음). Phase 2 착수 전 대상 API를 확정하고 실측해야 함 ([`tech-stack.md §9`](./tech-stack.md)).

### 축 5. 한국어·한국 데이터 환경 대응 (G8)

조사 대상 전체가 취약한 영역임.

- 리포트 전문 한국어 제공
- 인코딩 자동 감지(UTF-8 / CP949 / EUC-KR), 실패 시 사용자 선택 유도
- 한글 컬럼명, 한글 폰트 렌더링, 날짜 포맷(`YYYY-MM-DD`, `YYYY년 M월`) 파싱
- **이 영역의 시행착오를 콘텐츠로 발행함** — "CSV 인코딩 오류 진단", "한국 공공데이터 전처리 함정"은 영문 자료로 대체 불가하므로 information gain이 가장 높은 콘텐츠가 됨(축 6)

### 축 6. 지식 베이스 연동

도구 단독으로는 1차 타깃(입문자)에게 도달할 경로가 없음. 입문자는 사이트명이 아니라 **개념**을 검색함.

```text
검색 유입 → 해설 페이지 → [내 데이터로 확인하기] → 업로드 → 결과
                ▲                                          │
                └──────── Finding의 [자세히] 링크 ◀─────────┘
```

- 모든 Finding 유형은 대응 해설 페이지를 1:1로 가짐
- 결과 화면의 Finding에서 해설 페이지로, 해설 페이지에서 업로드로 양방향 연결
- **공개 사례 리포트** — 공개 데이터셋 분석 결과를 정적 문서로 발행. 업로드·로그인 없이 결과를 확인할 수 있어 데모 역할을 겸함

**콘텐츠는 추가 부담이 아님.** 축 1을 구현하려면 각 Finding 유형의 해석 문구를 어차피 작성해야 함. 툴팁으로만 소비하지 않고 독립 문서로 발행하는 것이 차이임. 부수 효과로 사이트 신뢰도와 수익화 요건(사전조사 §11)이 함께 충족됨.

상세 인벤토리·작성 순서·광고 정책은 [`content-strategy.md`](./content-strategy.md) 참조.

## 4. 단계별 범위

### Phase 1 — 코어 (MVP)
- CSV 파일 선택(업로드 아님 — 브라우저 내 처리), 인코딩·구분자 자동 감지
- 컬럼 타입 추론(수치·범주·날짜·불리언·ID·텍스트)
- 사전조사 §7 필수 기준선 9항목 전량 구현
- **Dataset Health Score** (축 2)
- **Finding 목록 + 규칙 기반 한국어 해석** (축 1)
- 데이터 타입 기반 자동 차트 선택, 대표 시각화 선별
- 웹 결과 뷰: 개요 / 품질 / 발견 / 변수별 / 관계 5개 섹션
- **필수 페이지 4종** — 소개·문의·개인정보처리방침·이용약관 (`noindex, follow`)
- **빌드 시점 HTML 생성 + MPA 구조 확보** — 모든 내부 URL을 확장자 없이 통일 (§6)
- 도구 화면에 설명·지원 형식·크기 제한·한계·FAQ 배치 (인터페이스만 있는 페이지를 만들지 않음)
- **완료 기준**: 10만 행 × 30열 데이터가 30초 내 처리되고, 결과 JSON 내보내기/불러오기로 재현 가능함

> Excel 지원은 파서 라이선스 확인 결과에 따라 Phase 2로 이동할 수 있음 ([`tech-stack.md §9`](./tech-stack.md)).

### Phase 1.5 — 콘텐츠 기반 구축 · **완료 (2026-08-18)**
- 해설 문서 20편 발행 (한국 데이터 환경군 3편 우선) — Phase 1에서 발화하는 Finding 유형 전량에 대응됨
- 공개 사례 리포트 3편 발행 — 데이터셋은 이용 조건 판정을 통과한 UCI CC BY 4.0 3건([`data-sources.md §4`](./data-sources.md))
- Finding ↔ 해설 페이지 양방향 링크 연결 (축 6)
- sitemap.xml, robots.txt, 정규 URL(확장자 없음), 페이지별 메타 태그
- Search Console 등록 및 색인 확인
- **완료 기준**: 콘텐츠 페이지 14편 이상이 색인되고, 모든 Finding 유형에서 해설 페이지로 도달 가능하며, **sitemap URL 전수가 307 리디렉션 대상이 아님**
- **현황**: 발행·링크·sitemap(27 URL, 리디렉션 0회)은 충족. **색인은 GSC 등록 대기 중**이므로 완료 기준 중 색인 항목만 미달임

### Phase 2 — 차별화 완성
- **단계별 분석 가이드 UI** (축 2의 STEP 흐름)

- 광고 배치 정책 구현 (§8) 후 **AdSense 신청 게이트** 조건 전량 충족 시 신청 — 게이트 조건은 [`content-strategy.md §7`](./content-strategy.md) 참조

## 5. 벤치마크 활용 방침

| 대상 | 활용 방식 |
|---|---|
| ydata-profiling | EDA 항목 커버리지 기준선. 산출 항목 누락 여부 대조에 사용 |
| DataPrep.EDA | 기능 구성·메뉴 구조 참고. 대용량 성능 열위 발생 시 엔진 대안 |

| AutoEDA (OSS) | Phase 3 전처리 확장 시 기능 범위 참고 |

**금지 방향**: "ydata-profiling보다 EDA 계산을 잘한다"는 경쟁 구도. 승산 없음. 채택 방향은 **"성숙한 엔진이 만들어내는 다량의 결과를 사용자가 실제 분석 과정에서 이해하고 활용하도록 재구성한다"** 임.

## 6. 기술 방향 (확정)

확정 스택·근거·배제한 대안은 [`tech-stack.md`](./tech-stack.md)에 있음. 요지만 옮기면:

| 영역 | 결정 |
|---|---|
| **분석 엔진** | **브라우저 JavaScript** (Web Worker). 무료 티어 Worker CPU가 요청당 10ms라 서버 연산이 불가하므로 연산을 클라이언트에 둠 |
| Finding 생성 | 통계 JSON에 규칙 엔진 적용 → Finding 객체 목록. 결정론적·무비용·테스트 가능 |
| 백엔드 | **없음.** 업로드가 없으므로 원본 데이터가 외부로 나가지 않음 |
| 프론트엔드 | 순수 HTML + 수기 CSS + Vanilla ES Module, MPA. 프레임워크·번들러 없음 |
| 콘텐츠 렌더링 | **빌드 시점 HTML 생성** (`md → HTML`). JSON+JS 런타임 렌더는 색인 코퍼스를 만들지 못함 |
| 차트 | 자체 SVG 렌더링 (5종). 라이브러리 없음 |
| 사례 리포트 | 손으로 쓴 원고 md → `build_guides.mjs` 가 정적 HTML 생성. 수치는 브라우저와 같은 엔진(`analyze`)을 Node 에서 돌려 뽑음 |
| SEO 요건 | sitemap.xml(결과 페이지 제외), robots.txt, **확장자 없는 정규 URL**, 페이지별 메타, Article 구조화 데이터 |
| 저장 | `localStorage` + 결과 JSON 내보내기/불러오기 |
| AI 연동 | 사용자 API Key를 저장하지 않고 요청 단위로만 사용 |

핵심 설계 원칙: **분석 결과는 JSON 데이터, Finding은 규칙 엔진 산출물, 시각화는 표현 레이어.** 세 층을 분리해야 리포트 형식 변경이 엔진 수정으로 번지지 않음. 구현상으로는 `js/domain/*`가 DOM·IO를 참조하지 않는 순수 함수만 갖는 것으로 이 계약을 강제함.

## 8. 비기능 요구사항

- 성능: Phase 1 기준 10만 행 × 30열 30초 이내. Web Worker에서 처리해 UI가 멈추지 않아야 함
- 데이터 취급: **파일이 브라우저를 벗어나지 않음.** 원본 무수정, 파생 산출물만 메모리·localStorage에 둠
- 보안: 사용자 API Key 미저장, 서버 전송 데이터 없음
- 초기 로드: 첫 진입 자산 총량을 1MB 이하로 유지 (34MB 초기 로드로 이탈 구조가 된 전례가 있음)
- 정보량: 컬럼 수가 많아도 기본 화면의 시각화 개수에 상한을 둠(선별 로직 필수). 구체 수치는 [`rules.md §4`](./rules.md)
- 보존: 브라우저 로컬에만 남으므로 사용자가 직접 삭제할 수 있는 수단을 제공함

### 광고 배치 및 색인 정책

| 페이지 | 광고 | 색인 |
|---|:---:|:---:|
| 랜딩 | ○ | ○ |
| 해설 페이지 / 사례 리포트 / 용어집 | ○ | ○ |
| 도구 화면 (진행·결과 상태 포함) | × | ○ — 단, **초기 HTML에 결과 UI를 두지 않음** |
| 소개 / 문의 / 개인정보처리방침 / 이용약관 | × | **× (`noindex, follow`) + sitemap 제외** |

**근거 2가지**

1. **결과** — 도구가 단일 페이지 4상태 구조라 결과에는 별도 URL이 없음([`screens.md §4`](./screens.md)). 초기 HTML에는 도구 설명·FAQ만 두고 결과 UI를 넣지 않으므로 **`noindex` 없이도 결과가 색인되지 않고**, 색인되는 것은 도구 설명뿐임. 광고를 제외해 UGC 정책 책임과 심사 리스크를 회피하고 분석 흐름 중간에 광고를 넣지 않아 UX도 지킴
2. **정책 페이지** — 심사자에게는 보일러플레이트로 읽히며, 색인 코퍼스를 차지하면 오히려 감점 요인임(실측 사례에서 보일러플레이트가 색인의 27%를 점유해 거절 사유가 됨). 있어야 하지만 코퍼스에는 들어가지 않게 함. 푸터 링크는 `follow`로 남겨 크롤러와 심사자가 도달할 경로를 유지함

> `noindex` 처리한 페이지를 `robots.txt`에서 `Disallow` 하지 않음 — 크롤이 막히면 Googlebot이 `noindex` 메타를 읽지 못함. 둘 중 하나만 씀.

개인정보처리방침에는 데이터가 브라우저를 벗어나지 않는다는 사실, 쿠키·개인화 광고 고지, 맞춤 광고 옵트아웃 링크를 기재하며 **실제 구현과 일치해야 함**.

## 9. 미결정 항목

확정 전에는 Phase 1 착수 범위가 고정되지 않음.

1. **커스텀 도메인 취득** — `workers.dev` 서브도메인에서는 `ads.txt` 루트를 소유할 수 없어 AdSense 신청 전 필요함. 콘텐츠 축이 닫힌 지금 **최장 리드타임 항목**이며, 도메인 선택이 곧 서비스명 확정임
2. **서비스명** — `AutoEDA`는 기존 오픈소스 프로젝트명과 충돌함. 1번과 함께 결정함
3. **Excel 파서 선정** — 라이선스 조건 확인 필요. 미해결 시 Phase 1은 CSV 전용 ([`tech-stack.md §9`](./tech-stack.md))
4. **인코딩 지원 범위** — `decode.js` 가 UTF-8·EUC-KR 두 가지만 지원함. 서유럽 인코딩 파일을 열지 못해 사례 후보 하나가 보류됐음([`data-sources.md §4`](./data-sources.md))

**결정된 사항**
- 처리 파일 크기 상한 — **개별 파일 25MB** (2026-08-16 확정). Cloudflare 무료 티어의 파일당 25MB 기준에 맞춘 값이며, 브라우저 메모리로 처리 가능한 범위임. 상수는 `js/domain/thresholds.js`의 `FILE_LIMIT`이고 초과 시 `FILE_TOO_LARGE` 오류 경로를 탐([`data-model.md §5.1`](./data-model.md))
- LLM 사용 — 사용자 API Key 기반 선택 레이어로 한정하며, 기본 기능은 AI 없이 완결함
- 기술 스택 — [`tech-stack.md`](./tech-stack.md)로 확정. 런타임·빌드타임 모두 JS(빌드타임 Python 은 계획했다가 쓰지 않음), 백엔드 없음, 프레임워크·Tailwind 미도입
- 배포 환경 — Cloudflare Workers Static Assets (형제 프로젝트와 동일)
- 인증·보존 기간 — 백엔드가 없어 서버에 저장되는 데이터 자체가 없으므로 쟁점이 소멸함
- 수익화 — AdSense를 콘텐츠 페이지에 한정 게재. 프로젝트 성공 기준으로 삼지 않음(사전조사 §11.5)
- 콘텐츠 작성 분량·주체 — **해소 (2026-08-18).** 초안 작성 후 검토 방식으로 24편·42,728자를 발행해 게이트를 넘겼음
- 사례 데이터셋 — **확정 (2026-08-18).** UCI CC BY 4.0 3건. 조건이 불명확한 후보는 제외했음([`data-sources.md §4`](./data-sources.md))
